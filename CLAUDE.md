# ZubuvZpevnikar (Zpěvníkář)

A desktop app (Linux first, other platforms later) for working on my LaTeX songbook:

1. Paste a URL of a chords website, and the song is converted to my LaTeX song format.
2. Edit the song `.tex` with syntax highlighting and a live PDF preview.
3. Assemble songbooks: pick which songs go into which project (the `\input` lists).

The app does not reimplement the songbook, its package or the converter. It drives three sibling repos.

## Terms (UI texts and docs)

- **Song library**: the folder the app opens (a ZubuvZpevnik checkout: `songs/`, `songbooks/`, the package). File → Open Song Library…, New Song Library…, `--library` (old name `--songbook`, still read).
- **Songbook**: one book in `songbooks/` (the Songbooks page). Never use "songbook" for the folder in UI texts. Code names (`songbookRoot_`, `openSongbook`, the `songbook/path` setting) are older and stay.

## The four repos

| Repo | Path | What it is | Docs |
|---|---|---|---|
| this one | `.` | C++23 / Qt 6 desktop app | `docs/PLAN.md` |
| ZubuvZpevnik | `../ZubuvZpevnik` | ~200 songs, songbook projects; the package as the submodule `zubuvzpevnik/` | `README.md` |
| zubuvzpevnik-package | `../zubuvzpevnik-package` (`zubuvzpevnik/` in the songbook, `external/zubuvzpevnik-package` here) | LaTeX package, classes, LilyPond includes, `scripts/` (build.sh, songidx.lua, checkpaper.py, the linters) | `README.md` (song format), `docs/building.md`, `docs/tools.md`, `docs/internals.md` |
| chords_converter | `../chords_converter` | Rust CLI: URL / saved HTML / text → LaTeX song | `README.md` |

- **The package** (`zub::package`): the app always builds with its bundled copy (`external/zubuvzpevnik-package`, a submodule pinned like the converter; installed into `share/zpevnikar/zubuvzpevnik`; `MainWindow::bundledPackage`; the source tree's copy only for programs run from the build dir, `ZUB_BUILD_DIR`), never with a song library's own `zubuvzpevnik/` submodule: that one would run unchecked under `-shell-escape`, so a library from someone else could bring its own code (decided with the user 2026-11-26). Keep the bundled pin in step with the commit ZubuvZpevnik's `zubuvzpevnik/` is pinned to, or the preview may differ from its releases. `MainWindow::packageDir_` is the one in use; every package path (TEXINPUTS, classes, LilyPond includes, `scripts/`) comes from it, never from `<songbook>/zubuvzpevnik`. A song library only needs `songs/chords/`. Package work happens in `../zubuvzpevnik-package`; once it is pushed, bump the pin like the converter's.

Read the sibling docs when a task touches them. Don't copy their content in here.

Key facts from them:
- A song is `songs/<collection>/<Artist>/<Title>.tex` (`\beginsong{Title}[by=..., key=...]` … `\endsong`). Collections are the folders under `songs/` (`chords`, `tinwhistle`: songs whose body is a `\lilypondfile` score; `zub::collections`, chords first). The input name "Artist/Title" is relative to its collection; the app finds songs and scores in every collection (preview and book TEXINPUTS, `resolveSongs`, `findScoreFile` own collection first). Import writes into `chords`; New Song asks. A new collection also needs the songbook's build scripts and the package's TEXINPUTS (not the app's to change).
- A songbook is a `.tex` under `songbooks/` (subfolders allowed: `songbooks/tabory/2025/tabor2025.tex`; older checkouts: `projects/`): a `\documentclass` from the package plus alphabetical `\input{Artist/Title}` lists in `songs` environments. `\beginkeeporder` … `\endkeeporder` keeps its songs in their order (the block sorts by its first song); `% TODO: Artist/Song` lines are wishes.
- Builds need `lualatex -shell-escape` (lyluatex runs `lilypond`), with `TEXINPUTS` pointing at the package, `songs/chords/`, the repo root and the book's folder. See `songbooks/velkyzpevnik/build.sh` in the songbook.
- A song header may have `tags={fav, label, ...}` (labels; `fav` = favourite, shown as ★; the songbook declares the key in `feature/metadata.cfg`). The app reads it with `zub::tags::parse` and writes it only through `zub::tags::setTags` (byte-exact for the rest of the header).
- `lang` may be a list (`lang={czech, hebrew}`): the first is the song's language (note and chord naming, index order, Tidy), the rest only tag it; the song list shows and filters by all of them (`zub::songLanguages`, `zub::mainLanguage`, ports of songfile.py's `song_langs`/`main_lang`).
- Song header parsing in `core/` (`zub::parseSong`, `zub::latex::*`) is a port of the package's `scripts/songfile.py`. Keep them in agreement; if one changes, check the other.
- Header options the app writes (`zub::songheader::setOption`: key, pap, tags, ...) go where the converter's order puts them (by, ori, tun, tem, met, cap, lang, key, tags, src, other keys, pap, chr: the converter's `prelude_rank`), and a value takes the place of its commented-out placeholder (`% key={},`), whose leftovers go; other keys' placeholders keep their place in that order. New Song's draft (`zub::songimport::newSong`) is in the same order.
- `pap` (the papers a song fits one page of; `a5x2` = two facing pages) is written only through `zub::songheader::setPap`/`setOption` with `checkpaper.py`'s rules (`measuredPapers`: the app offers it after a measurement, and after the Make Smaller/Join Lines proposals are applied (a background `shrink --fit --measure` of the new text), on a click; it never writes `x2`). Where the last paper goes, the key stays as `pap={}` (the converter's spelling; `checkpaper.py --write` removes the key instead).
- Linters (in the package's `scripts/`): `checksongs.py`, `checkkeys.py`, `checkpaper.py` (read-only, except `checkpaper.py --write`); they take `--songbook DIR`, else find the songbook above the package or the working directory.
- `chords_converter` is binary-only (no `lib.rs`); the app runs it as a subprocess (`ImportDialog`, `zub::songimport`). It writes `out/latex/<Artist>/<Title>.tex` relative to the **current directory**, prints `Saving output to: <path>`, exits 1 when the song could not be read or written and 2 for a wrong command line (converters before `9d00844` exited 0 after a failed write). `chords_converter convert <source> -o -` prints the song to stdout instead. Captured real outputs are in `tests/data/converter/`. The app finds the converter via `ZUB_CONVERTER` (an absolute path: a developer's converter build, tried before bumping the pin), next to its own executable (the built-in one), PATH, then `~/.cargo/bin`; no guesses. There is no choice in the UI (removed 2026-11-24 with the user; the old `converter/path` setting is deleted at start).
- `chords_converter` is also a git submodule at `external/chords_converter` (pinned to a commit on GitHub). CMake builds it with cargo and copies it next to the app (`ZUB_BUILD_CONVERTER`, on by default; skipped without cargo; an empty submodule folder is checked out at configure, `ZUB_FETCH_SUBMODULES`, never moving the pin). Converter work still happens in `../chords_converter`; once it is pushed, bump the pin with `git submodule update --remote external/chords_converter` and commit that. Never commit inside the submodule. The `[integration]` import test uses the converter in `ZUB_CONVERTER` (e.g. `build/debug/app/chords_converter`).
- The app needs converter **≥ 0.16.0** (`chords_converter --version`); the converter bumps the minor version whenever its command line, exit codes, `Saving output to:` lines or the proposals' JSON change. Always pass `--songbook <root>` and `--package <packageDir_>` to `shrink` and `join` (they would otherwise guess `../ZubuvZpevnik` and its submodule); `shrink --measure`, `join` (which always measures) and `shrink --apply` (Make Smaller's Make It Fit, `SongActions::startFit`: the paper of the listing, the song written with `-o` into the runner's temp dir and read back, `ConverterRunner::Options::readBack`; typing stops it) build the song with lualatex, so they need the preview's safety approval; `check` builds nothing.
- `tidy` reports each change on stderr as `<file>:<line>: <description>`, where the line is in the **input** text; the app maps it to the result with `zub::diff::mapOldLine`.
- The converter owns the song actions (`tidy`; `shrink`, `join`, `check` listing proposals as text-span edits, `apply` making them); the app only shows and applies them. See "Song actions" in PLAN.md. `shrink --measure` and `join` build the song with `lualatex -shell-escape` (via the songbook's `checkpaper.py`), so they need the same safety check as the preview.

## Architecture (hard rule)

```
core/    std-only C++23 library. NO Qt includes, NO Qt types. Links nothing from Qt.
         Song model, song .tex parser/writer, songbook project parser/writer,
         preparing external builds (zub::preview: files + command line) and reading their logs.
         core never starts processes: std C++ cannot run them asynchronously or cancel them.
app/     Qt 6 Widgets UI. Thin: owns windows, editor, PDF view, models for views.
         Converts std::string <-> QString / std::filesystem::path <-> QString only here.
tests/   Catch2 v3 unit tests for core/ (no Qt needed to build or run them).
```

- If something in `core/` seems to need Qt, stop and ask instead of adding the dependency.
- Prefer `std::filesystem`, `std::string_view`, `std::expected`/`std::optional`, ranges. No raw `new`/`delete` in `core/`.
- In `app/`, normal Qt idioms are fine: parent ownership, signals/slots. Keep logic out of widgets.
- Long-running work (lualatex, converter) must not block the UI thread. app/ runs it with QProcess (see `PreviewRunner`: newest request wins, the old process is killed).

## Build & test

```bash
cmake --preset debug                 # configure (Ninja, build/debug, compile_commands.json)
cmake --build --preset debug         # build
ctest --preset debug                 # run core unit tests (Catch2)
build/debug/app/zpevnikar      # run the app
QT_QPA_PLATFORM=offscreen timeout 3 build/debug/app/zpevnikar   # headless smoke test (exit 124 = ran fine)
```

- `--library <dir>` (old name `--songbook`) opens a song library for that run only; it is not remembered (`songbook/path` in `~/.config/Modrozoubek/ZubuvZpevnikar.conf` keeps the user's). Still prefer the app tests' fixture copies over running the app on `tests/data/songbook` (its stand-in classes can't build).
- `-DZUB_BUILD_APP=OFF` builds only core + tests (no Qt needed).
- Layout: public core headers in `core/include/zub/core/` (`#include <zub/core/...>`), namespace `zub`. App classes in `app/`, one class per `.hpp/.cpp` pair.
- New tests: add the `.cpp` to `tests/CMakeLists.txt`. Catch2 discovers the test cases.
- App tests (`tests/app/`, `zub_app_tests`, Qt + Catch2, run by `ctest` with the offscreen platform): they drive `MainWindow`, the Songbooks page, the editors and the score tabs through the static library `zpevnikar_app` (everything in `app/` but `main.cpp`). Internals are reached by `struct AppTestAccess` (`tests/app/AppTestAccess.hpp`, a `friend` of the tested classes: add a one-line friend and an accessor, never `#define private public`). Settings, cache and data go to a temp dir (`HOME`/`XDG_*` + `QStandardPaths::setTestModeEnabled`), every test copies the fixture into its own temp dir (`apptest::Fixture`; `Extras::Yes` adds `tests/app/data/extras/`: Test/Cz, Test/En, Test/Tun, Test/Two with scores, a two-language song, a whistle book) and never calls `openSongbook` with `remember`. Dialogs are answered by `apptest::answer*` (polling, not fixed sleeps). The runner is silent (no sound reaches the speakers; `ZUB_TEST_SOUND=1` to hear it), and any harness that can play audio must be muted the same way. Default runs empty `PATH` (no lualatex, lilypond, ...); cases tagged `[.tools]` need lualatex, lilypond, texlua, python3, fluidsynth or the built converter, are hidden from ctest and run with `build/debug/tests/app/zub_app_tests "[.tools]"` (each skips what it cannot find).
- Test data: `tests/data/songbook/` is a miniature ZubuvZpevnik checkout (copies of real tricky songs + `Broken/`). Tests get its path from `ZUB_TEST_DATA_DIR`; never read the real sibling repo from normal tests.
- `build/debug/tests/zub_core_tests "[integration]"` runs the hidden tests against the real `../ZubuvZpevnik` (e.g. every song parses). Run it after changing parsers.
- Warnings: every target links `zub_warnings` (`-Wall -Wextra -Wpedantic -Wshadow -Wconversion ...`). Keep the build warning-free.
- Formatting is `.clang-format` (a hook runs clang-format on C++ files Claude edits). clangd reads `build/debug/compile_commands.json` via `.clangd`.

## Releases and CI

- `.github/workflows/ci.yml`: core (Ubuntu), the app (Fedora 42), and Windows (`windows-2022`, MSVC, Qt 6.8.3 from aqt, KF6 SyntaxHighlighting built by `.github/actions/kf6-syntax-highlighting`): all tests pass there since 2026-11-24 and the job must stay green (Windows paths, `;` in TEXINPUTS, no open files while replacing them); the MSVC environment comes from `vcvars64.bat` in a step of its own (no Node 20 action).
- `.github/workflows/release.yml`: a tag `v<VERSION of CMakeLists.txt>` builds the Linux AppImage (Ubuntu 24.04, Qt 6.8.3 from aqt, `packaging/appimage.sh` with linuxdeploy) and attaches it to a GitHub release; run by hand it only builds the artifact. Both build jobs run the tests first; the packaging scripts refuse a build without the converter or the package. Its actions are pinned to commits and linuxdeploy (only "continuous" builds upstream) to checksums: when upstream rebuilds it, the release fails at the check until the new checksums are tried and written in. Workflows read only (`contents: read`, `persist-credentials: false`); only the release job writes. CI also fails when `update_translations` would change the `.ts` files. The user tags and pushes, never Claude.
- Run as an AppImage (`$APPIMAGE`), the app writes its launcher entry and icons into `~/.local/share` on every start where they changed (`DesktopIntegration`, `zub::desktopentry::forAppImage`: Exec/TryExec = the AppImage, marker `X-Zpevnikar-AppImage=true`); an entry without the marker (e.g. from `cmake --install`) is never replaced or removed. Settings → "Show Zpěvníkář in the application menu" (`desktop/menuEntry`, only shown for an AppImage).
- Windows: one codebase; the OS-specific parts have a Windows variant: TEXINPUTS `;` (`zub::preview::kPathListSeparator`), paths written with `/` (`toQString`, the core's commands), paths as text only in UTF-8 (`toQString`, `toUtf8`/`pathFromUtf8` in `app/convert.hpp`, `u8string` in core; never `path::string()`, `generic_string()` or a path from a `std::string`: Windows' ANSI code page throws on Czech names), stopping a program with what it started (`processtree`: Unix process group, Windows job object with kill-on-close, the program created inside it (a job list in its startup info; `prepare` sets the QProcess's CreateProcess arguments modifier); every QProcess that runs lualatex, lilypond, fluidsynth, bash, Python, the converter or git goes through `processtree::prepare`/`terminate`/`kill`), bash and Python (`externaltools`: Git for Windows' bash.exe, never System32's WSL bash; python3/python/py, not the Store stubs; probed once on a worker thread at start, with `chords_converter --version`). `zpevnikar.exe` has its icon (`app/zpevnikar.rc`) and no console. The Release workflow also makes `Zpevnikar-<v>-windows-x64.zip` and `Zpevnikar-<v>-setup.exe` (`packaging/windows/package.ps1`: cmake --install, KF6 DLL, windeployqt, a start check, Inno Setup `zpevnikar.iss`). Not yet tried on a real Windows machine: the songbook build through Git's bash, and the index order (`locale -a` does not exist there; songidx.lua's locale).

## Translations

- UI texts in `app/` go through `tr()` (`QCoreApplication::translate` with a fixed context outside QObject classes). Counts use `tr("%n song(s)", nullptr, n)`, never `.arg(n)` plus "(s)". Give short ambiguous texts a disambiguation comment.
- After changing UI texts run `cmake --build --preset debug --target update_translations` and translate the new entries in `app/i18n/zpevnikar_cs.ts` (Czech, three plural forms). `zpevnikar_en.ts` only holds the English plural forms; fill the new `%n` entries there too.
- Core and converter messages stay English. The language is `ui/language` in the settings ("" = system, "cs", "en"), applied at start in `main()`.

## Guardrails

- **Sibling repos are not ours to restructure.** ZubuvZpevnik has CI and GitHub releases. Never commit, push, or change their layout, scripts or class files without asking. Editing song `.tex` files and project `\input` lists is the app's job and is fine when the task is about that.
- **Previews never write into `../ZubuvZpevnik/build/`.** Build previews in a temp dir (the app's cache dir, or `tmp/` here). Reuse `build/tmp-ly` only by symlink/read.
- Don't write in `../chords_converter/` (e.g. adding a `lib.rs`) without asking.
- Song files are Czech-heavy UTF-8. Keep encodings and line endings intact; don't reformat songs.
- Preview builds run in `QStandardPaths::CacheLocation/preview` (kept between builds for LilyPond's `tmp-ly` cache), from the editor's text via a song copy in `override/` that shadows the real file on TEXINPUTS. Errors come from `lualatex -file-line-error`; real logs for tests are in `tests/data/logs/`.
- Build files (Settings → Build files, `buildfiles`, `build/keepFiles`, default keep): kept, LilyPond's `tmp-ly` (by a hash of each score) makes a rebuild engrave only changed scores (velkyzpevnik: 16 s instead of ~100 s); otherwise `PreviewRunner` deletes the preview's `tmp-ly` and `BookPreview` the book's `repo-<hash>` work dir once their build has ended (the PDF is in memory). Settings shows their size and Delete Now (`MainWindow::deleteBuildFiles`: not what a running build of this window uses). `buildfiles::remove` deletes only a `tmp-ly` in the cache or a `repo-*` in `songbooks/`. Kept, a successful build marks the scores its log names as used (`zub::scorecache::usedScores`: lyluatex logs "Compiling score tmp-ly/<md5>" for every score, cached or not; `buildfiles::keepUsed` sets their files' modification time) and deletes the scores no build used for 30 days (`buildfiles::unusedFor`); `pruneWorkDirs` deletes book work dirs and other instances' `preview-<pid>`/`score-<pid>` dirs unchanged for as long (never this instance's own).
- **Songs are code.** Previews run `lualatex -shell-escape`, so `\directlua` etc. in a song would run with the user's rights. `zub::safety::unknownConstructs` checks songs against an allowlist (`knownSongCommands`): the commands real songs use plus every user command of the songs package, except the ones that open files by a name from the song (`\newindex`, `\newauthorindex`, `\newscripindex`, `\showindex`) and primitives like `\csname`; songs with anything else are never built automatically and only after confirmation. When the song format gains a command, add it to the allowlist (the `[integration]` test fails otherwise). Never weaken this check to make a test pass.
- Songbooks are only the LaTeX books in the songbook repo's `songbooks/` (the app keeps none of its own since 2026-11-16).
  - `zub::bookfile` reads and writes them byte-exactly: `findBooks`, `parse`, `setSongs`, `readSettings`/`setSetting` (class and options, title, author, camp year, cover, chord chart), `addSection`/`renameSection`/`removeSection`/`moveSection`, `setLocked`, and `newBook`/`buildScriptFor` for New Songbook and Duplicate (a .tex and a self-contained build.sh).
  - Wish and comment lines move with the input below them, a removed input with a note is commented out, and a `% \input{X}` is uncommented on adding.
  - Every real book must round-trip (`[integration]`).
  - The page's LaTeX tab edits the whole file. Its unsaved text blocks the other edits, so there is one writer at a time.
  - A file changed on disk since it was read is never overwritten.
  - `% zpevnikar: locked` (`lockMark`) marks a released book: nothing changes it until Unlock.
  - The Preview tab (`BookPreview`) builds on a button, never by itself, and Export PDF saves its PDF (building first when out of date). A book's PDF builds from a copy in `CacheLocation/songbooks/repo-<hash>/` with `<package>/scripts/build.sh -i <indexFiles>` (`zub::bookfile::buildCommand`), never with the folder's own `build.sh`. `TEXINPUTS=".:<work>:<package>[:<override>]::<repo>/songs/<every collection>:<bookDir>:<repo>"` puts the package and then TeX's own tree (the empty entry) first, so no folder of the library can stand in for a file of the package or of TeX's tree (`relsize.sty`, lyluatex); files neither has (an optional `hyperref.cfg` a package probes for) are still looked for in the library's folders, so every build first checks them with `zub::songbook::texinputsShadows` (any file at the top of `songs/<c>/`, TeX-loadable names in the repo root and the book's folder, scores under the book's folder; part of the build's risks, confirmed like a song's); then the songs, so nothing beside the book or in the repo root can stand in for them; the preview has the same order (`.:<override>:<package>::<songs>:<repo>`, the repo root last). Collection names must be `[A-Za-z0-9_-]+` real folders (`zub::validCollectionName`; others and links are ignored): they go onto TEXINPUTS and into build.sh. `scoreRisks` checks every copy of a score a build could find (each collection's, the book folder's when given, the repo root's).
  - The book file and a Tabor book's chord chart must pass `zub::safety::unknownBookConstructs` or be confirmed: every `akordy.tex` the build could find (`zub::bookfile::chordChartFiles`: each collection's top folder comes before the book's own on TEXINPUTS, the repo root's stands in when the book has none), as must index files (`*.sbx`, `*.sxd`) in those folders. `buildScriptFor` (Duplicate) refuses book and index names that are not plain (`zub::safety::isPlainName`: they go into build.sh unquoted), and Duplicate copies a cover only by a plain relative path (`isPlainFilePath`). Every `\input` must be a song, and the songs get the song check. When a book gains a command, add it to `kBookKnown`.
- **Scores are code too.** A song's `.ly` files (`\lilypondfile{Artist/X.ly}`, found in the song's own tree first: `songs/chords` for a chords song, `songs/tinwhistle` for a tinwhistle song, then the other; `zub::songbook::resolveScoreReference` normalises the name like lyluatex, and a reference that is not an in-tree `.ly` is an unapproved risk, as is a call without a braced argument or with `[options]`, `zub::songbook::unreadableScoreCalls`: the package's `\lilypondfile` takes one token) run Scheme in lilypond. LilyPond looks for an `\include` beside the score first, so a `zubuvzpevnik.ily`/`tinwhistle.ily` (any case) next to a score is a risk too (`zub::songbook::includeShadows`). `zub::safety::lilypondRisks` flags `#(`/`$(` forms other than `#(ly:make-moment N N)`, `$name`, any other character after `#`/`$` (whitespace, `@`, `;`, `!`, `|`), and `\include` of anything but `zubuvzpevnik.ily`/`tinwhistle.ily`; data forms (`#'sym`, `#'(...)` read with Scheme's lexical rules, `##t`, `#RIGHT`, ...) are fine. The same approval rule as for songs applies to the score preview and to the song's PDF preview (which checks the referenced scores, from the editors and from disk), to the songbook PDF export and to the scan's measuring (`zub::songbook::scoreRisks`). Real `.ly` files must keep passing (`[integration]`).
- Score files are named `<SongFileName><PartName>.ly` next to the song (`HeartOfGoldGuitarIntro.ly`; `Jolene.ly` for a song's only score; every real score follows it). New Score asks only for the part name (`zub::score::partName`, `scoreFileName`).
- Score preview: `lilypond -dbackend=svg -dcrop -I <package>/lilypond -I <work>/score -o <work>/out/score score.ly` in `CacheLocation/score` (`zub::score::prepare`; the `out/` directory must exist, `LC_ALL=C` keeps the log English). `score.ly` is `\language "english"` (`"deutsch"` for lang czech/slovak, `zub::score::germanNames`, mirrors `zubuvzpevnik.sty`) plus `\include` of the score copy. Unsaved scores reach the song's PDF preview through `zub::preview::Request::fileOverrides` (`override/Artist/X.ly` shadows the real file on TEXINPUTS).
- Fretboard input (`zub::fretboard`, `FretboardWidget`, `ScoreInputBar`): the tuning comes from the **score text**, never from the song's `tun` header: that of the staff at the editor's cursor (`tuningAt`: guitar unless the staff's `stringTunings` is `banjo-open-g-tuning`; in a variable's definition the staves that play it, outside any staff the whole-score `tuningOf`), unless the input bar's Tuning combo (per score tab, session only) forces Guitar or Banjo; note names from the song's `lang`/`key`. Notes are absolute-octave `pitch\string` tokens; a duration is written only when it differs from `effectiveDuration`. Clicks on the fretboard only *stage* positions (one per string, drawn as filled dots; rings show the ONE selected note or chord, none for a cursor between notes); selecting exactly one event with positions (`positionsOfEvent`: every note has a `\N`) loads them into the staging and the Insert button becomes Replace: `replacePitches` swaps only the note-or-chord part (prefixes, duration, ties, articulations stay; a rest takes the notes, `q` is refused; a chord note's own prefix is lost), one undo step, the event stays selected; the staging goes when the selection moves off it. Insert (button or Alt+N, the Edit menu action `ScoreTabs::insertStagedAction`, enabled while something is staged on the current score tab; Ctrl+Enter in the editor opens a line below, Ctrl+Shift+Enter above) writes them as one note or one chord `<lowest string ... string 1>` in one undo step, Clear (Escape) drops them, a double-click stages and inserts at once. Staging is cleared when the tuning changes. Note-input keys (only with the score preview or the fretboard focused, never the text editor: `ScoreInputBar::isInputKey`/`handleKey`): 1 2 4 8 (6 = 16) length, . dot, r rest, | bar check; the selection actions (Tie, Slur ...) are a button row always shown under the editor. The preview's click-to-note uses LilyPond's `textedit://path:line:col:col2` links (0-based code-point column) of the score copy only.
- Score regions (`zub::scoreregion`, `SvgCanvas` caret and drag, `SongEditor::applyRegionAction`): all text transformations of selected notes (tie, slur, glissando, repeat, strokes, dead notes) are core functions on a byte range of the score text, using the tokeniser shared with `zub::fretboard` (`core/src/scorescan.hpp`: change it in one place). The app maps the preview's link positions to music events (`offsetOf` line/column -> byte offset, `musicEvents`, `eventAt`; only links into music events are selectable) and selects whole events in text order; `[integration]` `every action on the real scores` runs every action over every real score; the score caret sits between notes like a text cursor (a click left of the picked note: its event's begin, right of it: its `Range.end`; drag and Shift+click select the events between the two caret offsets, double-click exactly one event); one undo step per action; keyboard on the preview (it takes the focus on a click, clicks no longer focus the editor): Left/Right/Shift/Home/End move over `caretStop`s of the events, Backspace/Delete call `zub::scoreregion::removeEvents` (`SongEditor::deleteScoreEvents`; keeps durations, slur/beam partners and dangling ties right; `[integration]` `deleting each event`), Ctrl+Z/Y undo; offsets are into `SongEditor::editorText()` (LF, raw text), not `content()` (CRLF files).
- Playback (`zub::midi`, `PlaybackRunner`, `ScorePlayer`, `NoteSounds`): the preview build of a score also writes a MIDI file (`score::Request::midi` appends a second `\score` with `\unfoldRepeats` and `\midi`, tempo from the song's `tem` x the tempo combo, transposed up by the song's `cap` since tabs are written in the capo's shapes, so no extra lilypond run or safety path); Play only runs `fluidsynth` on that `.mid` (WAV cached by hash, silence trimmed) and plays it with QMediaPlayer. Fretboard clicks play a one-note MIDI rendered once per pitch (QSoundEffect), also raised by the capo. Instruments are chosen per staff (`zub::score::staves`: `\new Staff`/`\new TabStaff` of the first `\score`; ids in `zub::midi::instruments()`, "auto" = as the file sets it, else by score; in a score with several staves a tab staff plays the banjo only when its own `stringTunings` is banjo): kept in memory per score for the session (`ScoreTabs::staffChoices_`, no settings), in the MIDI score as `\with { midiInstrument }` per staff (`MidiOptions::staffInstruments`; a file's leading `\set` of that staff is overridden in the copy only) and in fret clicks (the staff at the cursor). Chord names (`\new ChordNames`, `\chords`; `zub::score::hasChordNames`) are silent unless their own row in the Instruments list picks an instrument (`MidiOptions::chordInstrument`, session only per score, no saving; amp chords count as an amp staff). The hidden melody (`\new Devnull`, `zub::score::hasHiddenMelody`) has a row "Melody (lyrics)" that defaults to Voice (`ScoreTabs::showStaves`, `ScorePreviewPane::melodyChoice_`); Silent stays selectable. "Save to file" (`zub::score::saveStaffInstrument`) writes `\set Staff.midiInstrument = "<GM name>"` at the start of the staff's music, one undo step; `amp` is saved as General MIDI's `"distorted guitar"` (`zub::midi::ampFileName`), which `findInstrumentByName` and a staff left on Automatic read back as `amp`. `amp` (Distorted electric guitar) is the clean electric guitar whose audio goes through `zub::audio::applyAmp` in place on a worker thread (mixed signal: chords intermodulate), keyed in the WAV cache by `ampId` + `ampVersion` (raise it when the sound changes); when only some staves use it, `prepare` appends two `\book`s (`zub-playback`, `zub-playback-amp`, the other group muted with `\remove "Staff_performer"`), `PlaybackRunner` renders both, amps the second and mixes them (`zub::audio::mixWav`); fret notes for it are `<program>-<pitch>-amp.wav`. Bends, pre-bends, releases and slides play as pitch bends (a slide from a grace note, `\grace g\3 \glissando e'4`, is a fast slide at the start of the main note: the grace note and the time it took go, `markerSlideIn`): the MIDI score marks them (`zub::score::markBends`: a one-moment `midiInstrument` change to a sound-effect program, no Scheme) and `PlaybackRunner` runs `zub::midi::smoothBends` over the `.mid` before fluidsynth (`bendVersion` is in the WAV cache key). Needs `fluidsynth` + a GM soundfont, else the buttons are disabled. The score cursor is the play position (`zub::scoretiming`, `ScoreTabs::buildTimeline`/`startSeconds`/`followAt`): Play starts at the note at the editor cursor or the start of the selection (its first pass when repeated; 0 before the music or when the text changed since the build, `scoreLinksFresh_`) by seeking the WAV (`ScorePlayer::play(file, startMs)`; the trimmed silence is only the tail, so MIDI time is WAV time), and a 30 ms timer puts a plain cursor right behind the note that began last at the player's position (`cueAt`; of events that begin together the last one the preview shows; `followAt` computes cue, cursor, editor marks and preview boxes from that one time and updates the preview's caret at once, bypassing the highlight timer); `startSeconds` therefore takes a caret right behind a note as THAT note (so Stop then Play resumes at the note that sounded; a caret in the gap before a note starts at that note); after the end the caret stays and, unmoved (`endedAt_`), Play replays from 0; a click or caret move of the user during playback (editor or preview) restarts the player at `startSeconds` (a selection: its first note; `playingWav_`, `seekMs_` waits for the player's new position) and following goes on; an edit stops the following and the playback (the timeline is stale), as does a new build, a tab switch, Stop and the end. Where each note sounds comes from the generated playback \score only: its `\layout` (`\Score skipTypesetting`, nothing is drawn, no measurable cost) `\consists \zubNoteLogger` in `Voice`, `TabVoice`, `ChordNames`, `Devnull` and `Lyrics`, a fixed Scheme engraver that `prepare` writes to `workDir/zub-playback.ily` (included by the wrapper `score.ly`, never by the user's file) and that appends "kind (n note, c chord name, m silent melody, l lyric), moment, origin, event length" of each note event (lyric event in `Lyrics`) to `out/zub-playback.notes` (`parseNotes` still reads the old kind-less lines). Besides the cues (staff notes only: what the editor selects) the timeline has `sounds` (`soundingAt(seconds)`: every staff note or chord, chord name and lyric syllable with start <= t < end; a Devnull note is no sound but gives the length of the syllable that begins with it, else a syllable lasts to the next one; chord names and lyrics in the generated copy map back to the block by the n-th occurrence of their word, skipped when the counts differ; length 0 or unknown sounds `minimumSounding` 0.12 s), and `ScoreTabs::showSounding` draws them as orange boxes (`ScorePreviewPane::setSoundingNotes`) on the preview's links inside those texts (`linkOffsets_`) and marks the same ranges in the editor (`SongEditor::setPlaybackMarks`, `CodeTextEdit::setPlaybackMarks`, a translucent orange extra-selection layer like the search marks, not a selection); a lyric's or chord name's box ends at the rendered text's right end (`NoteLink::textRight`, measured from the SVG's `<text>` with QFontMetricsF and its font-family/size; the character-count estimate only without one); Melody sounds (Devnull notes, `Kind::Melody`) have no cue and are marked in the text only; with the default Voice instrument the hidden melody is a staff voice (Kind::Note). Stop, the end, an edit or a new build clear them, links that do not exist are skipped. That Scheme is ours and fixed (only the output path varies), so it is not part of `lilypondRisks` and the user's score must still pass it unchanged; do not add anything user-controlled to it or to the generated `\layout`, and keep `#(` out of the appended score (`appendIsNeutral` checks that). The amp's second book has no listener (same music). `zub::scoretiming::buildTimeline` pairs the notes written in the generated copy of the first \score's music with the text's music events in order (it fails, no following, when the counts differ) and converts moments with `zub::midi::tempoMap`; `[integration]` `every real score builds an SVG and a MIDI file` checks every real score, `the timeline is the same for every way the playback score is built` the amp variants. Notes of a single-note or single-chord variable definition are no music events and have no cue.

## Workflow

- Work milestone by milestone from `docs/PLAN.md`; tick items off there.
- For non-trivial features, plan first (plan mode), then implement, then run the tests, then the `cpp-reviewer` agent.
- Agents in `.claude/agents/`: `songbook-latex` (LaTeX/song format, builds, linters), `chords-converter` (the Rust CLI), `cpp-reviewer` (read-only review of C++ changes), `cpp-implementer` (Sonnet, writes code from a precise spec).
- Division of labour (an experiment, started at milestone 2): the main session designs APIs and does cross-cutting work; well-specified implementation goes to `cpp-implementer`; `cpp-reviewer` (Opus) reviews. Compare cost and quality per milestone and adjust.
- Skills: `/preview-song <path>`, `/import-song <url>`, `/new-feature <description>`.
